## 🌅 上午（第1-3章）

### 第1章：整洁代码（1.5小时）

**核心观点：**
- 衡量代码质量：**WTF/min**（每分钟咒骂次数）
- 糟糕代码代价：维护成本高、后期生产力趋向零
- **破窗理论**：对烂代码放任不管，会变本加厉
- **童子军军规**：每次提交代码要比检出时更干净

**关键引用：**
> "细节之中自有天地，整洁成就卓越代码"

---

### 第2章：有意义的命名（1.5小时）

**核心原则：**
- 读代码时间 >> 写代码时间（>10:1）
- 好的命名节省的时间远大于起名时间

**最佳实践：**

| ✅ 要 | ❌ 不要 |
|-------|---------|
| 名副其实 | `l`, `1`, `0`, `O` 易混淆字符 |
| 避免无意义区分 | `Product` vs `ProductInfo` vs `ProductData` |
| 有意义区分 | `mainThread` vs `signalHandlingThread` |
| 避免编码 | 除非项目规范要求（如 `m_` 前缀） |
| 类名用名词 | `Customer`, `WikiPage` |
| 方法名用动词 | `postPayment`, `deletePage` |

**案例：**
```java
// ❌ 差
int d; // 什么鬼？
List<int> lst = new ArrayList();

// ✅ 好
int elapsedDays;
List<Account> accounts = new ArrayList<>();
```

---

### 第3章：函数（1.5小时）⭐最重要

**核心原则：**

1. **短小**：函数应该只有 10-20 行
2. **只做一件事**：每个函数只有一个目的
3. **抽象层次一致**：高层次函数只调用同层次函数

**最佳实践：**

```java
// ❌ 差：函数太长，做了多件事
public void submit() {
    validateInput();
    connectToDatabase();
    saveToDatabase();
    sendEmail();
    logActivity();
    updateUI();
}

// ✅ 好：每个函数只做一件事
public void submit() {
    validateInput();
    if (!isValid) return;
    
    saveOrder();
    notifyCustomer();
    updateUI();
}
```

**函数参数原则：**
- 最好 0 个参数
- 其次 1-2 个
- 尽量避免 3 个以上

**标志性军规：**
> 每个函数下面嵌套层级不超过 2 层

## ☀️ 中午（第4-5章）

### 第4章：注释（30分钟）

**可以出现的注释：**
- 法律信息
- 公开接口的语义说明
- TODO 注释
- 解释复杂业务逻辑

**要避免的注释：**
- 过期的注释
- 解释烂代码的注释（应该重写代码）
- 注释掉的代码

**原则：**
> 注释是代码表达失败时的补救措施。如果需要注释，先尝试用代码表达。

---

### 第5章：格式（30分钟）

**工具化：**
- 使用 Prettier、clang-format、ESLint 等工具
- 配置保存/提交时自动格式化

**垂直格式：**
- 紧密相关的代码放在一起
- 遵循团队规范 > 个人喜好

**规则：**
- 调用者放在被调用者上面
- 相关函数放在一起

## 🌙 下午（第7、10章）

### 第7章：错误处理（45分钟）

**核心原则：**

1. **使用异常而非返回码**
```java
// ❌ 差
if (save() == OK) {
    // 继续
} else {
    // 处理错误
}

// ✅ 好
try {
    save();
} catch (SaveException e) {
    // 处理错误
}
```

2. **不要返回 null**
```java
// ❌ 差
public User findById(String id) {
    return null; // 调用者需要检查
}

// ✅ 好
public Optional<User> findById(String id) {
    return users.stream()
        .filter(u -> u.getId().equals(id))
        .findFirst();
}
```

3. **不要传递 null**

---

### 第10章：类（45分钟）⭐ SRP

**单一职责原则（SRP）：**
> 一个类应该只有一个改变的理由

**如何判断类太长：**
- 类名包含 `Processor`、`Manager`、`Super`
- 超过 500 行

**类组织顺序：**
1. 公共静态常量
2. 私有静态变量
3. 私有实例变量
4. 公共函数
5. 私有函数（被公共函数调用）

## 🌟 晚上：实践与复习（2小时）

### 实践任务

1. **代码 Review**：review 自己或同事的代码，找出 3 个可以改进的地方
2. **重构练习**：找一个自己写的函数，尝试拆分成更小的函数
3. **命名检查**：检查项目中是否有 `temp`、`data`、`info` 等无意义命名

### 自检清单

- [ ] 函数是否短小（<20行）？
- [ ] 命名是否清晰、顾名思义？
- [ ] 是否有注释解释烂代码（应该重写而非加注释）？
- [ ] 错误处理是否使用异常？
- [ ] 类是否遵循单一职责？
- [ ] 是否使用工具自动格式化？
